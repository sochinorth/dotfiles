# setup

Arch (CachyOS repos), reproducible with `mise bootstrap` (mise ≥ 2026.9).

## Layout

| File | What it is | Sources |
| --- | --- | --- |
| `mise.toml` | Generic, for any machine (servers, routers too): repos, doas/fudo, shell, CLI, Kakoune, `/etc` basics, dotfiles | `files/`, `dotfiles/`, `scripts/` |
| `mise.dev.toml` | Dev module: toolchains (clang, cmake, mingw-w64, bun, pip), debuggers, gh, direnv, just, kakoune-lsp + kak-tree-sitter; coding agents: OpenCode with its config, pi, Claude Code as a runtime for OpenCode (no config); user units: OpenCode's server, `opencode.web-gui` (OpenCode Web with GUI plugins on :44444), dropbear on :22222 (SSH in without root) | `dev/` |
| `mise.wsl.toml` | WSL module: `wsl.conf`, xclip → win32yank shim, the stock /tmp cleaner unmasked (WSLg's X socket exempt), `.wslconfig`, Windows PATH, win32yank (AUR), the Npcap loopback keepalive (a Windows scheduled task, for mirrored loopback) | `wsl/` |
| `.miserc.local.toml` | Per machine, gitignored: which modules a plain `mise bootstrap` loads | |
| `dotfiles/config/kak` | Kakoune: kakrc, kakbr, `kakmux`/`kakbr-sidebar`/`broot-open`, `kak()`/`kakbr()`; the [kakmux](https://github.com/sochinorth/kakmux) repo as a submodule, with its own tests | mise links each file (`[dotfiles]`) |
| `dev/opencode` | OpenCode (v2): the global `opencode.json`, `cli.json` (the TUI's: theme), `AGENTS.md` (global instructions: workflow state goes in the project scratchpad, never in the project), `plugins/codex-sale` (live models with catalog capabilities and limits), `plugins/compaction` (compaction into a tree: an index in context, the session's whole transcript in its scratchpad, large tool outputs filed whole; native for OpenAI models; `/compact <focus>`), `plugins/claude-entrypoint` (Claude launch environment), `plugins/claude-transcripts` (deletes Claude transcripts of deleted sessions), `plugins/follow-tools` (unfolds the grouped tool block the agent is working in, folds it when it moves on), `plugins/native-search` (web search through OpenAI's and Claude's own search tools), `plugins/scratchpad` (a scratchpad per project, and one per session inside it, deleted with the session), `plugins/tool-descriptions` (a short description on every shell and file-change call, shown in the timeline), `web-gui.ts` (desktop GUI plugins in OpenCode Web, through a local proxy; the `opencode.web-gui` unit runs it), and `build` (builds plugins' GUI parts) | mise links `opencode.json`, `AGENTS.md` and the plugins into `~/.config/opencode`, seeds `cli.json`; `post-dotfiles` runs `build` |
| `dev/skills/idasql` | [idasql-skills](https://github.com/allthingsida/idasql-skills), pinned as a submodule (skills and their references, unchanged upstream) | mise links each skill into `~/.config/opencode/skills/idasql-*`, giving it an IDASQL-prefixed ID |
| `dotfiles/fortune` | fortune cookies fortune-mod doesn't ship: its offensive (`-off`) set, which Arch builds without, and others (sources below) | mise links each into `~/.local/share/fortune`; `post-dotfiles` runs `strfile` |
| `README.local.md` | Per machine, gitignored: notes about this machine (what isn't captured, where) | |

```sh
mise bootstrap                 # generic + modules from .miserc.local.toml
mise -E wsl bootstrap          # generic + WSL, explicitly
mise -E dev,wsl bootstrap      # generic + dev + WSL (this dev box)
MISE_ENV=none mise bootstrap   # generic only, overriding .miserc.local.toml
mise bootstrap unapply wsl     # remove what the WSL module manages
mise bootstrap unapply dev     # turn a dev box back into a generic one
```

Each module keeps what it brings in its own directory (`wsl/`, `dev/`), so `dotfiles/`,
`files/` and `scripts/` are only the generic part's. What a module adds to `.zshrc` goes in
`~/.config/zsh/conf.d/*.zsh`, which `.zshrc` sources: each deploys its own drop-in
(`wsl/zsh/wsl.zsh`: Windows PATH; `dev/zsh/dev.zsh`: bun's globals, pi, the direnv hook).

**Adding another platform** (e.g. bare metal): create `mise.baremetal.toml` with
its sources in `baremetal/`, and select it with `-E baremetal` or in that machine's
`.miserc.local.toml`. Generic parts that are still machine-specific (the znver4 repos
in `files/etc/pacman.conf` and the Zen 4 check in `scripts/pre-packages.sh`) would
move into modules too, if the new machine has a different CPU.

## Fresh machine

```sh
# 1. as root, once (creates the user, wheel, doas.conf; plus wsl.conf under WSL)
pacman -Sy --noconfirm git && git clone <this repo> /tmp/setup && /tmp/setup/install-root.sh

# 2. WSL only: from Windows
wsl --terminate archlinux

# 3. as your user
git clone --recurse-submodules <this repo> ~/setup && cd ~/setup
mise trust && mise -E dev,wsl bootstrap --dry-run && mise -E dev,wsl bootstrap   # drop dev on a server/router, wsl on bare metal
```

Then copy `~/.ssh/id_ed25519_*` over by hand (keys are deliberately not in the repo). Hosts that only matter on one machine go in `~/.ssh/config.local`, which `~/.ssh/config` includes.

With dev, sign the coding agents in again: credentials stay out of the repo. Claude Code: sign in once with `claude`, for OpenCode's Claude Agent provider. OpenCode: `/connect` each provider (codex.sale, OpenRouter, DeepSeek, ...). pi: its own sign-in (it keeps it in `~/.pi/agent/auth.json`).

The Kakoune config (`dotfiles/config/kak`) and IDASQL skills (`dev/skills/idasql`)
are submodules, cloned over HTTPS (no keys needed yet). A clone made without
`--recurse-submodules` gets them from the `pre-dotfiles` hook; by hand,
`git submodule update --init`. After pulling a commit that moves one,
`git submodule update` (that checks out the recorded commit: commit and push
work in the submodule first).

IDASQL skills are loaded by OpenCode itself, not through Claude Code's plugin
marketplace. Start with `@idasql-connect`; all 16 skill IDs are prefixed
(`idasql-analysis`, `idasql-decompiler`, `idasql-xrefs`, etc.). OpenCode derives
IDs from each linked directory's basename; a parent grouping directory would
not namespace them. Display names and cross-skill names in the upstream text
remain unchanged: for example, its `connect` means `idasql-connect` here.
To update, run
`git -C dev/skills/idasql pull --ff-only` and record the new submodule commit.

## Order of operations, and why

mise runs as your user and elevates with `sudo`. On this setup `sudo` is
**fudo-git**, a shim that turns sudo calls into **doas** (`permit persist keepenv :wheel`).
That dependency chain fixes the order:

1. `install-root.sh` (root): user in `wheel`, `opendoas`, `/etc/doas.conf`. There is no sudo yet.
2. `pre-packages` hook (`scripts/pre-packages.sh`, through doas):
   - imports the CachyOS and Chaotic-AUR keys, installs the mirror lists and `pacman.conf`
   - installs the keyrings, then reinstalls everything from the znver4 repos (CachyOS's own procedure)
   - installs `paru` (prebuilt, cachyos repo), removes real sudo only after `doas true` succeeds, then `paru` installs fudo-git
3. `[bootstrap.packages]`: pacman, now through sudo → fudo → doas; `aur:` entries through paru, which uses the stock `/etc/paru.conf` and elevates through sudo → fudo → doas too. Don't create an empty `~/.config/paru/paru.conf`: any user file replaces `/etc/paru.conf` and loses its defaults.
4. `[bootstrap.files]`: `/etc` configs; with WSL, also the `/usr/local/bin/xclip` → `win32yank.exe` shim.
5. The `pre-dotfiles` hook (checks out missing submodules), `[dotfiles]`, then the `post-dotfiles` hooks: `scripts/post-dotfiles.sh` (broot `br` launcher, tealdeer cache, fortune indexes), then with dev `dev/post-dotfiles.sh` (pi and its shims, linger for the user units, kak-tree-sitter grammars). Hooks from each file add up; a module's hook doesn't replace the generic one.
6. With dev, the user units (`dev.mise.opencode.service`, `dev.mise.opencode.web-gui.service`, `dev.mise.dropbear.service`, enabled and started); then login shell → zsh; with WSL, the `final` hook writes `.wslconfig` on the Windows side.

## Gotchas captured here

- **Never install `base-devel`**: it depends on `sudo`, which conflicts with fudo-git.
- The **znver4 repos** need a Zen 4+ CPU. The hook refuses to run on anything else.
- `makepkg.conf` (`-march=native -O3`, LTO) is not tracked: it ships that way in CachyOS's `pacman`.
- WSL: `appendWindowsPath = false` in `wsl.conf`. The WSL drop-in adds back only System32; `win32yank.exe` comes from the AUR (`win32yank-bin`) into `/usr/bin`, since a Windows exe runs from the WSL filesystem too. The Windows home isn't configured: the `final` hook asks PowerShell for `%USERPROFILE%`, in the same call as the RAM size.
- WSL: by default WSL shuts the distro down (a `systemctl poweroff`, user units and all) 15 s after its last terminal closes; `.wslconfig` turns that off (`instanceIdleTimeout=-1`), so the user units keep running until `wsl --shutdown` or `--terminate`. `.wslconfig` changes apply only after one of those.
- WSL: `.wslconfig` (mirrored networking; `memory=` 85% of the host's RAM, filled in then) is written to the Windows side by the `final` hook, not symlinked, and not a `[dotfiles]` entry (its path depends on the Windows user).
- Cookies in `dotfiles/fortune`, each as published (checked 2026-10-13, all at their latest): the `-off` files are [fortune-mod](https://github.com/shlomif/fortune-mod)'s `datfiles/off/unrotated`; `archlinux` from the AUR's fortune-mod-archlinux; `billwurtz` from [Ev1lbl0w/fortune-mod-billwurtz](https://github.com/Ev1lbl0w/fortune-mod-billwurtz); `g` is [ketogenesis/gfortune](https://github.com/ketogenesis/gfortune)'s `gsource`; `lambda` is [LAMBDA.TXT](http://www.gotlisp.com/lambda/lambda.txt) v11; `linuxorgru` is the lorquotes.ru dump (2021.07, via the AUR's fortune-mod-lorquotes; the site is gone). Plain `fortune` (stock build) shows the `-off` ones like any others.
- btop rewrites its own config, so that one is a copy. After changing settings in the app, run `mise dot add <path>`.
- broot opens files in Kakoune: Enter is a verb in `verbs.hjson`; double-click is hard-wired to the system opener, so `broot-open` is also installed as `wslview`/`xdg-open` in `~/.local/lib/broot-opener`, a dir only broot gets on PATH (`broot()` in kakmux's `shell/kakmux.zsh`, which `.zshrc` sources; `kakbr-sidebar`). In `kakbr`'s sidebar both go to kakbr's kak; elsewhere in tmux, to a kak pane in broot's window (kakrc labels each kak client's pane). `kakmux` and `kakbr` each run their own tmux server (`kakmux-PID`, `kakbr-PID`), so each is one pane in whatever runs it; kakbr's right pane is just a `kakmux`.
- kak-tree-sitter turns off Kakoune's own highlighting for every language it knows, grammar installed or not. So kakrc writes `~/.config/kak-tree-sitter/config.toml` (not tracked; regenerated when the installed set changes) to hand every language without a grammar back to Kakoune. The dev module's post-dotfiles hook installs a handful (C/C++, Rust, Python, Bash, Markdown, TOML, JSON, YAML); add more with `ktsctl sync <lang>`.
- Claude Code is only a runtime: OpenCode's Claude Agent provider starts `claude` with `--setting-sources=` (no settings files), `--tools=` (OpenCode's tools over MCP instead), and hooks, CLAUDE.md and auto memory off. Only managed settings (`/etc/claude-code`) would still reach it, so there are none.
- `plugins/claude-entrypoint` sets Claude Agent's launch environment in the OpenCode server, which the SDK inherits: `CLAUDE_CODE_ENTRYPOINT=opencode`, instead of the SDK's default `sdk-ts`, and `CLAUDE_CODE_DISABLE_ARTIFACT=1`, which drops Claude Code's own scratchpad (see below). OpenCode's shell commands don't get them, so a `claude` run from one stays standalone: it keeps its artifacts, and `claude-transcripts` leaves its transcripts alone. Other server child processes inherit them, MCP servers and terminals included: a `claude` started in an OpenCode terminal is tagged `opencode`, so `claude-transcripts` treats its transcripts as orphans, which a later sweep deletes once they're an hour old and no `claude` has them open (if the database and Claude dir are both default or both overridden), unless it's started with `env -u CLAUDE_CODE_ENTRYPOINT -u CLAUDE_CODE_DISABLE_ARTIFACT claude`. Processes already running (Claude, the PTY daemon behind persistent terminals) keep the environment they started with. The variables stay set in the server until it exits, even if the plugin is unloaded, and a location that unloads it no longer filters its shell commands.
- Claude still writes a transcript per OpenCode session to `~/.claude/projects`, and it's load-bearing: Claude Agent resumes from it (`--resume`) every time it restarts `claude` (5 minutes idle, a detached client, a server restart) and forks it on edit or revert. Without it OpenCode resends the conversation as flattened text. OpenCode never deletes these transcripts, so `plugins/claude-transcripts` does: when a session is deleted, and at load for sessions deleted meanwhile, along with the provider's record linking the two, plus OpenCode-started transcripts no record points to (orphaned by forks) once they're an hour old and no `claude` process has them open. That record is private to the provider, so the plugin reads it from OpenCode's database directly: a changed format makes it log and do nothing.
- Web search (`plugins/native-search`): OpenCode's own `websearch` providers are search services (keyless and rate limited, or with a key), and a Console connection makes its hosted search, billed per query, the default. The plugin adds providers backed by the vendors' own search: `openai` (`gpt-6-luna` with `web_search`, on the ChatGPT login through the Codex backend, or an API key) and `anthropic` (`claude -p` with only WebSearch, Haiku, on Claude Code's login and `claude-entrypoint`'s environment, saving no session). A third, `native`, picks by the model searching: Claude Agent models get `anthropic`, OpenAI's `openai`, others the plugin's `fallback` (`openai`). A provider is told only the query, so it's matched to the websearch call its session just made, whose model the plugin tracks per session. `opencode.json`'s `websearch.provider` selects `native`, and a Console workspace's own choice would otherwise override it. The tool, its `websearch` permission rule and the timeline stay OpenCode's.
- Claude Agent sessions don't get Claude Code's own WebSearch: an `OPENCODE_CLAUDE_PATH` wrapper could add it to `--tools`, but the provider forwards only OpenCode's tools, so searches would bypass the timeline, the permission rule and OpenCode's history.
- Scratchpads (`plugins/scratchpad`): OpenCode on its own points every session at `/tmp/opencode`, one directory shared by every session and project, which the `/tmp` cleaner ages out after 10 days. The plugin keeps them in `~/.local/state/opencode/scratchpad/` instead: a session working in `/home/me/repo` gets the project scratchpad `-home-me-repo/` there (named after the session's directory the way Claude Code slugs it, so a worktree is its own project) and its session scratchpad `-home-me-repo/<sessionID>/`. Subagents share their root session's, a fork starts with a copy of its source's, a session moved to another directory takes its own along, and deleting a session deletes only its own directory (at load too, for sessions deleted meanwhile); the project scratchpad and other sessions' stay. Session directories from before projects (`<sessionID>/` right under the root) move into their project when their session is next used, with an instruction entry mapping old paths to new. The model learns the paths from a session instruction entry (`scratchpad`); unlike a system prompt edit, that also reaches Claude Agent sessions. For the other providers the `/tmp/opencode` hint is dropped from the environment block. `AGENTS.md` builds on it: workflow state goes in the project scratchpad, a directory per task, groomed like the in-repo `.wip/` it replaces, so a task outlives its session and another model can pick it up.
- Claude Code has a scratchpad of its own, `/tmp/claude-<uid>/<slug>/<Claude session ID>/scratchpad`, that it names with "always use it" in the first turn's environment block, whatever the system prompt (Claude Agent's is Claude Code's `claude_code` preset with OpenCode's agent role and instructions appended, hardcoded in the provider). Files there are invisible to another model taking the session over, and the path changes with every fork. Claude turns it on when a server-side flag (`tengu_scratch`) says so or when its Artifact tool is available; the flag is off here, and `CLAUDE_CODE_DISABLE_ARTIFACT=1` (set by `plugins/claude-entrypoint`) makes the Artifact tool unavailable. Claude Agent gives Claude no built-in tools anyway, so a captured request differs in that one line only. Should the flag turn on, the line comes back. The next lever would be a Claude Code mod (its `prompt.attachment` event rewrites messages Claude Code adds itself; untried), but under OpenCode's `disableAllHooks` only a mod counting as an organization's runs, which takes managed settings.
- Tool-call descriptions (`plugins/tool-descriptions`), like Claude Code's Bash `description`: the server part makes `description` (5-10 words) a required input of the shell, edit, write and patch tools as the model sees them; the tools ignore it, and the stored call keeps it. Its `gui/` puts it in the timeline: Shell rows read `Shell  <description>  <command>` and open into the output; file changes fold under an `Edit  <description>` line (`Write`, or `Edits` for a mix) that opens into the diffs (the files' names stand in for a missing description: the field isn't enforced, and models do skip it); and a Thought whose summary fits on its header line (GPT's usually do: they're mostly a heading) shows it there, after `Thought 5s`, with no dropdown, while a longer one stays as the app shows it, unfolded with its arrow to fold. That's DOM decoration, as there's no timeline hook, so an app update can silently stop it. It's the plugin's GUI part, which OpenCode Desktop loads, and OpenCode Web too when opened through `web-gui` (below). It's built by `dev/opencode/build` (whose `node_modules` would otherwise sit in the plugin's directory, which OpenCode watches whole), not tracked: rerun its `bun run build` after editing `gui/`. It reads best with Settings › Timeline › Advanced set to Shell collapsed, Edits not collapsed (the fold is the plugin's), Thinking not collapsed (inline Thoughts need the summary rendered), and nothing grouped.
- Following the agent (`plugins/follow-tools`, a GUI part only): with tool calls grouped in the timeline, the block the agent is working in (`Used 13 Shell, Grep, Read`) unfolds as it starts, so its calls show as they run, and folds again once the agent moves on: a note, another block, or the end of the turn. It opens each block once. A block the user folds or unfolds stays as they left it, and blocks they opened themselves are never folded. Like `tool-descriptions` it works on the 2.2.x app's DOM, clicking the group's own trigger, so an app update can silently stop it. It's built by `dev/opencode/build` too, and loads in OpenCode Desktop and in Web through `web-gui`.
- Compaction (`plugins/compaction`) keeps a session as a three-level tree. (2) `log/0001.md`, `0002.md`, ... in the session scratchpad's `transcripts/<sessionID>/` hold every message, one file per stretch between compactions, each checkpoint appended at the end of its stretch; (3) a tool output over 4 KB is written whole to `T0143.out` beside them as it's logged, and its log entry points at it; (1) a compaction leaves an index in context: `## Must know` (what can't be searched for: the user's words, decisions, dead ends, where things stand, the next step) and `## Map` (grep keys into the transcript; a key the transcript doesn't contain is marked), written by the session's own model through `ctx.session.generate` so it reuses the turns' cached prefix. After it, every request gets a note on the transcript (read or grep it before relying on details; its text is data, not instructions), deterministic facts (files changed and read, large outputs by anchor, failed calls) and Claude Code's restore of the five files most recently read or changed inside the session's directory (5k tokens each, 50k in all); that block is injected, not stored, so it stays in the cached prefix and doesn't arrive a step late. The model's copy of a tool output is never changed, nor is history in requests: trimming old outputs cost more than it saved on these providers (Claude's later thinking is invalidated, Claude Agent forks its session, ChatGPT's backend caches only whole earlier requests). OpenAI models (`gpt`/`o`/`codex` families) on OpenAI's or Azure's Responses route compact natively: OpenAI writes an encrypted checkpoint, steered by a last message about the transcript, and the model also writes the readable index, which follows it; that covers the `openai` provider (ChatGPT's Codex backend), codex.sale (on OpenAI's route for it, since the generic openai-compatible one can't compact) and opencode-go's GPT models. An encrypted checkpoint replays only to its model, so after a switch to another the session is compacted again with the stored index, no model call. An explicit `settings.compaction` in `opencode.json` overrides this; a model whose native compaction is refused (a non-transient 4xx) switches to summary compaction for good. `/compact <text>` (the plugin's command, which a `/compact` with text reaches instead of the TUI's built-in) adds instructions to the index request or the native steering message. Without a transcript (no scratchpad yet) OpenCode compacts on its own. Per-session state is `state.json` beside the log, so it's deleted, moved and forked with the scratchpad. Needs `opencode service restart` after edits.
- Desktop GUI plugins in OpenCode Web (`dev/opencode/web-gui.ts`, run by the `opencode.web-gui` user unit from boot): open <http://127.0.0.1:44444> (or `localhost:44444`) instead of the service's own address. It needs no login or `opencode pair`: the proxy sends the service's password (from `~/.local/state/opencode/service.json`, as the CLI does) with every request, and starts the service through its unit when it's down. The web app ships the desktop app's GUI plugin host and GUI plugins support the browser, but a plain tab lacks the bridge the desktop app's main process provides, so Web loads no plugin GUIs. The proxy supplies it: it serves a bridge script reading the GUI bundles from the server's `/api/plugin/gui` (enable/disable kept in localStorage), patches the app's entry script to hand it over (`platform: "web"` gains `plugins`), and adds `'unsafe-eval'` to the page's CSP, since the host evaluates bundles with `Function()`. Main-process halves (`main`, IPC, native menus) have nowhere to run and report unavailable. If an update changes the entry script's shape, the patch is skipped with a log line and Web runs plain. It checks for new or rebuilt GUI bundles every 15 s while the tab is visible. Since the proxy logs in for whoever reaches it, it serves only its own pages: it answers only to its loopback names (`127.0.0.1`, `localhost`, `[::1]` on its port; DNS rebinding gets a 403), and refuses browser requests from another origin or site (`Origin`, `Sec-Fetch-Site`: other localhost ports count as the same site, so they're refused too). Non-browser clients get in; under mirrored networking that includes Windows processes, which as you could read `service.json` through `\\wsl.localhost` anyway.
- OpenCode also discovers `~/.claude/skills` independently of the Claude Agent provider. `dev/opencode/opencode.json` blocks the eight Claude-synced skill IDs (`built-in-browser`, `chrome-browser`, `computer-use`, `docs`, `docx`, `pdf`, `pptx`, `xlsx`) with `skill.use` policies: they expect Claude-specific tools. Claude's files stay untouched. The rules match IDs, not source paths; newly synced IDs need their own rule.
- OpenCode runs as a background service, started at boot by the `opencode` user unit through a login zsh, so its agents' commands get a terminal's environment. `opencode service restart` from a terminal works too, but the server it starts runs outside the unit (closing the terminal doesn't stop it); `opencode service stop; systemctl --user start dev.mise.opencode` restarts it under systemd, and once it's there `systemctl --user restart dev.mise.opencode` does. The service caches a plugin's module by path: after editing `plugins/codex-sale`, restart it (a config reload re-runs the old code). Its config watcher misses edits to `opencode.json` made here, through the symlink: `touch -h ~/.config/opencode/opencode.json` makes it reload. Its credentials, sessions and model picks are in its database, `~/.local/share/opencode`. It's the pacman package, so update it with pacman, not `opencode upgrade`.
- pi (`@earendil-works/pi-coding-agent`, a bun global) runs `node`/`npm`/`npx`, and there's no Node here: `~/.local/pi-shims` holds bun under those names, and the `pi` alias (`dev/zsh/dev.zsh`) puts it first on PATH for pi alone.
- Dropbear (dev) serves only you, since it runs as you, and keys only: the ones in `dev/ssh/authorized_keys`, copied (not linked) to `~/.ssh/authorized_keys`. Its host key is generated on the unit's first start in `~/.config/dropbear/`, so a new machine has a new one.
- Not captured: secrets (SSH keys, app credentials), project checkouts, timezone/hostname files that WSL generates. What that means on a given machine goes in its `README.local.md`.
